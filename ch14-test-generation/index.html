第 14 章 · Part 4：進階能力

測試生成：plan / generate / heal

CLI 內建與 Playwright Test MCP 同一套策略，但用本地快照。

⚠️
plan / generate / heal 不是 CLI 子指令

實測（0.1.19 版）：playwright-cli plan --help、generate --help、heal --help 都不是可辨識的指令——playwright-cli 遇到不認得的字，就直接印出整份 --help，跟打錯字沒有區別；playwright-cli --help 完整指令表裡也確實沒有這三個字。 它們其實是 CLI 內建技能包（references/test-generation.md）裡定義的三個工作階段，教 agent 怎麼組合既有指令——attach、snapshot、resume、pause-at、step-over、generate-locator，配合 npx playwright test --debug=cli——走完「探索 → 產出測試 → 修復」這三步，不是三個能直接打的動詞指令。以下維持 plan / generate / heal 的說法，因為這是官方文件與 skill 本身使用的階段名稱，但請記得它指的是流程，不是 playwright-cli 的子指令。

三個階段

階段做什麼
Plan先確保有 seed test（把頁面帶到每個情境的起始狀態），再用 npx playwright test --debug=cli 背景跑 seed、playwright-cli attach tw-XXXX 接上暫停的瀏覽器，靠 resume / snapshot / click / eval 探索 app，最後把結果寫成 specs/<feature>.plan.md 這份測試計畫（核心工作流、邊界情境、斷言點）
Generate依 spec 裡的步驟，一樣用 attach 接上暫停的 seed test 逐步操作；每個動作 CLI 都會印出對應的 Playwright TypeScript，收集起來寫成正式測試檔，斷言用 generate-locator 產生的定位手動補上
Heal測試跑失敗時，用 npx playwright test <file>:<line> --debug=cli 在失敗點附近暫停、attach 上去用 snapshot / console / requests 診斷是選擇器漂移還是 app 真的壞了，修完測試檔再視情況同步 spec

這套流程跟 Playwright Test MCP 的對應 agent 是同一套邏輯，差別在 CLI 用本地 snapshot，不把 raw DOM 灌進對話。

plan → generate 怎麼串起來用

實務上 Plan 和 Generate 很少單獨做，而是接成一個兩階段流程：先讓 agent 驅動 live app 產出測試計畫（標出核心工作流、live DOM 驗證與缺口），寫成 specs/<feature>.plan.md 這份 Markdown（不是 YAML），再把計畫轉成重用既有 Page Object 的測試檔——價值不只是磁碟上那份 Markdown，而是 agent 產出它的過程中發現了什麼。第 16 章 有完整的實戰範例，含可以直接複製的 prompt 與三份產出物清單。

與 @playwright/test runner 的橋接

測試生成是 playwright-cli 這一側的能力；真正跑測試套件還是 @playwright/test。兩者的接點是： 用 npx playwright test --debug=cli 把某個測試暫停，agent CLI 再 attach 到那個暫停的瀏覽器，接手診斷或補步驟。

常見踩雷

  • Generate 出來的測試仍需人 review 斷言與邊界——它是草稿，不是成品。
  • Plan 依賴 live DOM，目標頁面要進得去、狀態要對。
  • Heal 能救小改動（改個 class、換個 label），大改版還是要人重寫。
  • 把 plan / generate / heal 打進終端機當 CLI 指令 → 不存在，這三個字是 skill 文件裡的階段名稱（見上方提醒），實際操作靠 attach / snapshot / resume 等既有指令組合。
