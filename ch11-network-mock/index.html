第 11 章 · Part 4：進階能力

網路攔截與 Mock：route / unroute

不改後端，就能驗證前端在各種 API 回應下的行為。

三個指令

route <pattern> [opts]   # 攔截符合 pattern 的請求，回傳你指定的內容
route-list              # 列出目前生效的 route
unroute [pattern]       # 移除某個 route；不帶 pattern 則清空全部

pattern 用 glob，** 比對任意路徑片段。

常見用法

# 偽造一個 JSON API 回應
playwright-cli route "https://api.example.com/**" \
  --body='{"mock":true,"data":[]}' \
  --content-type=application/json

# 模擬 404
playwright-cli route "**/avatar.png" --status=404

# 清掉所有攔截
playwright-cli unroute

典型場景：

  • 驗證前端在空清單、錯誤碼、逾時、離線時的畫面與提示。
  • 把不穩定的第三方 API 換成固定回應，讓探索 / 測試可重現。
  • 在後端還沒好時，先用 mock 把前端流程跑起來。
⚠️
--body 裡的大括號要處理引號與跳脫

--body='{...}' 在 shell 裡要用單引號包住整段 JSON；由 agent 發指令時，注意它有沒有幫你正確跳脫。內容複雜時，改把 JSON 寫成檔案、或用 run-code --filename 走完整 Playwright page.route()。

route 是 session 級的

攔截規則跟著 session 走。換一個命名 session（見 第 10 章）規則就不生效； 重新導航通常會保留規則，但把瀏覽器 close 掉就沒了。用 route-list 隨時確認目前掛了哪些。

allowedOrigins / blockedOrigins：限制，但不是防護

設定檔的 network.allowedOrigins / blockedOrigins（或環境變數 PLAYWRIGHT_MCP_ALLOWED_ORIGINS / _BLOCKED_ORIGINS） 可以限制瀏覽器能請求哪些來源。規則：blocklist 先於 allowlist 評估；同時命中兩者的來源被擋。

🚫
官方明講：這不是安全邊界

allowedOrigins / blockedOrigins 不作為安全邊界、也不影響 redirect。它適合「讓測試環境不要不小心打到 production API」這種用途，不適合當隔離手段——真要隔離用 OS / 容器層。

看實際流量

搭配 DevTools 指令確認攔截有沒有生效：requests 列出頁面載入後的所有請求，request <index> 看單一請求細節，console 看前端有沒有因為 mock 回應報錯。這些在 第 12 章 一起講。

常見踩雷

  • pattern 忘了 **，只寫 https://api.example.com/users → 對不到帶 query string 或子路徑的請求。
  • 在 A session 掛 route、卻在 B session 操作 → 沒作用。
  • unroute 不帶 pattern → 一次清光，不是只清一條。
