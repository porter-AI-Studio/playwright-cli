第 9 章 · Part 3：核心操作模型

元素定位：ref、CSS selector、Playwright locator、find

預設用 ref，但另外三種在特定場景更穩、更適合寫進腳本。

四種方式一次看

方式長相適合風險
snapshot refclick e15agent 即時互動、探索短命，頁面變動就失效，跨 run 不穩
CSS selectorclick "#main > button.submit"結構穩定的頁面、你很熟 DOM 時SPA / A/B test / 改版下脆弱
Playwright locatorclick "getByRole('button', { name: 'Submit' })"寫進腳本、要跨 run 穩定需要頁面有語意化 role / label
findfind "Add to cart"在大快照裡先定位、再取 ref是搜尋不是操作，仍要回到 ref

ref：預設，但不要硬記

沒特別指定時，就用 snapshot 裡的 ref 操作。它的好處是你不用寫脆弱的 CSS 路徑；壞處是它只對「產生它的那份 snapshot」有效。 規則很簡單：先 snapshot，再用當下的 ref，操作後若頁面變了就重新 snapshot。細節見 第 7 章。

CSS selector 與 Playwright locator

ref 之外，click / fill 這些指令也吃 CSS selector 和 Playwright locator 字串：

# CSS selector
playwright-cli click "#main > button.submit"

# role locator（跨 run 穩定，推薦寫進腳本）
playwright-cli click "getByRole('button', { name: 'Submit' })"

# test id
playwright-cli click "getByTestId('submit-button')"

getByTestId 對應的屬性名預設是 data-testid，可用設定檔的 testIdAttribute 或環境變數PLAYWRIGHT_MCP_TEST_ID_ATTRIBUTE 改。

💡
探索用 ref，固化用 locator

agent 邊探索邊操作時用 ref 最省事；等流程要寫成可重複執行的腳本，把關鍵步驟換成 getByRole / getByTestId——它們不會因為一次 re-render 就失效。這條分界貫穿 第 16 章 與 第 17 章。

generate-locator：把 ref 轉成穩定 locator

探索時你手上是 e12，要寫進腳本時可以請 CLI 幫你轉：

playwright-cli generate-locator e12
# 輸出類似：
#   page.getByRole('link', { name: 'TypeScript' })

這是「用 ref 探索、用 locator 落地」最直接的橋。Playwright 的 codegen / recording 也偏好產生getByRole、getByText 這類語意化定位，原因相同：避開脆弱的 CSS 路徑。

用 find 縮小範圍

快照很大時，先用 find 把範圍縮到你要的區域，再從命中結果取 ref：

playwright-cli find "結帳"
playwright-cli find --regex "/add to (cart|bag)/i"

它回傳的是匹配節點加上下文，不會把整份快照吐給你——省 token，也讓 agent 更快鎖定目標。

常見踩雷

  • 在動態頁面上重複使用舊 ref → 先重新 snapshot。
  • 用 CSS selector 選到會隨 A/B test 或 render 改變的 class → 改用 role / testId。
  • locator 字串裡的引號跟外層 shell 引號打架 → 內外用不同引號，或把複雜字串寫進檔案用 run-code --filename。
