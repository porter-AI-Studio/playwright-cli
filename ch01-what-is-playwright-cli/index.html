第 1 章 · Part 1：認識 Playwright CLI

Playwright CLI 是什麼，以及為什麼 AI agent 需要它

一個把「讓 AI 看見並操作瀏覽器」這件事，重新設計成「一連串省 token 的 shell 指令」的工具。

一句話定義

Playwright CLI（npm 套件名 @playwright/cli，可執行檔名 playwright-cli）是 Microsoft 在 2026 年初推出的命令列瀏覽器自動化工具，專門為 coding agent 設計。它跟既有的Playwright MCP出自同一個團隊、底下是同一顆 Playwright 引擎，差別在於「怎麼把瀏覽器的狀態餵給模型」。

Playwright MCP 走的是Model Context Protocol——一個 JSON 格式的 AI ↔ 工具通訊標準；Playwright CLI 則直接是 shell 指令，你的 agent（Claude Code、GitHub Copilot、Codex、Cursor……） 透過 Bash 工具呼叫它，就像呼叫 git 或 npm 一樣。

ℹ️
官方定位：companion，不是取代

官方把 Playwright CLI 描述成 Playwright MCP 的「companion」（伴隨工具），不是要取代它。兩者的取捨會在 第 2 章 完整展開；簡短版是：有 filesystem 和 shell 的 coding agent 用 CLI，沙盒環境或需要 MCP 協定的自動化用 MCP。

為什麼 AI agent 需要它：context window 是一筆有限的預算

每個 AI coding agent 都活在一個 context window 裡——一筆固定的 token 預算，同時裝著對話歷史、 你打開的程式碼檔案、工具的輸出、還有模型推理需要的一切。這筆預算一旦見底，session 就開始遺忘前面的內容、 甚至直接中斷。

用 Playwright MCP 驅動瀏覽器時，每navigate到一個內容豐富的頁面，一次 browser_navigate 就可能回傳 數千 token 的 accessibility tree；每截一張圖，整張圖的位元組都會變成 token 灌回 context。一個多步驟的自動化流程跑下來， 這些量疊加得非常快。對「context 已經塞滿原始碼、測試結果和對話」的 coding agent 來說，這不是小小的最佳化問題， 而是「這個 session 到底跑不跑得完」的差別。

核心設計：資料存磁碟，不進 context

Playwright CLI 的關鍵設計只有一句話：把東西存到磁碟，讓 coding agent 自己決定要讀什麼。

從模型的角度看，每個指令都很小、而且幾乎沒有狀態：

  • 跑 playwright-cli snapshot，得到一份精簡的 YAML 檔，裡面是帶著 e21、e35 這類引用（ref）的元素樹。
  • 跑 playwright-cli click e21，用 ref 操作某個元素。
  • 跑 playwright-cli screenshot，把一張圖存到磁碟。

在這整個過程裡，完整的頁面 DOM 和圖片二進位從來不會被塞進模型的 context——除非 agent 自己明確去讀那些檔案。 指令回傳的通常只是一行檔案路徑加一句確認訊息。

agent 下指令：playwright-cli snapshot
↓
頁面完整結構 → 寫成 .playwright-cli/page-xxxx.yml
↓ 回傳給 agent 的只有這一行
「Snapshot 已存到 page-xxxx.yml」＋當前 URL / title
↓ agent 自己決定
要嘛整份讀進來、要嘛用 find 只搜需要的節點、要嘛根本不讀

一次真實的操作長什麼樣

下面是一段自動化 TodoMVC 範例站的 session——正是 coding agent 在做測試時會跑的那種流程：

# 開瀏覽器（預設 headless；加 --headed 可以看到畫面）
playwright-cli open https://demo.playwright.dev/todomvc/ --headed

# 取一份快照，拿到元素 ref
playwright-cli snapshot
# 快照存成 YAML 檔，內容像這樣（精簡的元素樹）：
#   - textbox "What needs to be done?" [ref=e8]
#   - checkbox "Toggle Todo" [ref=e21]

# 新增幾筆待辦
playwright-cli fill e8 "Write Playwright tests"
playwright-cli press Enter
playwright-cli fill e8 "Review test coverage"
playwright-cli press Enter

# 勾掉第一筆
playwright-cli check e21

# 截圖存證
playwright-cli screenshot
# 已存：.playwright-cli/page-2026-02-12T05-27-11-604Z.png

注意每個指令回傳的東西都很小——一行檔案路徑、一句確認。agent 從頭到尾沒有處理過一份一萬 token 的 accessibility tree，也沒有把一張五萬 token 的截圖吃進 context。它拿到的是 e8、e21 這種精簡引用，直接拿來用。

💡
連 skill 都不裝也能用

Playwright CLI 有一組給 agent 讀的 skill 檔（第 4 章），但就算不裝，也能直接叫 agent：用 playwright-cli 測試 https://demo.playwright.dev/todomvc 的「新增待辦」流程，先看 playwright-cli --help 有哪些指令。 agent 會自己讀 --help 學會怎麼用。

token 帳單：官方 benchmark 說了什麼

Playwright 團隊自己的 benchmark 顯示，一個典型的瀏覽器自動化任務：

方式該任務的 token 消耗相對倍數
Playwright MCP約 114,000 tokens基準
Playwright CLI約 27,000 tokens約 1/4

差距主要來自兩件事：

  • 快照存檔，不隨回應內嵌。MCP 導航到頁面時，會把完整的 accessibility 快照放在工具回應裡回傳——就算 agent 只需要找一顆按鈕。 CLI 把快照存成磁碟上的 YAML，回應裡只有一行路徑，agent 可以選擇讀、或不讀。
  • 截圖永遠不進 context。MCP 下模型要一張截圖，圖的位元組就會進 context window。CLI 把截圖存成.playwright-cli/ 裡的 PNG；如果任務只是「截圖存檔」（測試流程裡很常見），模型根本不需要看到那些像素。
⚠️
「Playwright CLI」有兩種意思，別搞混

2026 年以前，很多文章講的「Playwright CLI」指的是 @playwright/test 內建的 npx playwright screenshot / codegen / open 這組子指令。本書講的是 2026 年新出的 @playwright/cli——一套獨立套件，有自己的 snapshot / ref / session / dashboard / skills。兩者安裝方式與指令名稱都不同，照抄舊教學會踩雷。完整釐清見 第 3 章。

它不是什麼

  • 不是 @playwright/test 測試 runner。npx playwright test 是拿 spec 檔跑測試套件的；playwright-cli 是跨多次終端呼叫、操控一個活著的瀏覽器。一個專案可以同時裝 @playwright/test 和 @playwright/cli。
  • 不是你的測試框架的替代品。它讓 AI coding agent 在「開發與除錯階段」更會操作瀏覽器——產生 E2E 測試草稿、診斷 UI bug、做探索性測試——正式的回歸測試還是交給測試框架跑。
  • 不是要跟 Playwright MCP 二選一。常見用法是混搭：探索階段用 MCP 邊看邊想，流程確定後用 CLI 固化成可重複執行的腳本（第 17 章）。

需要準備什麼

門檻很低：

# 需要 Node.js 18 以上（部分官方文件寫 20+）
node --version

# 全域安裝
npm install -g @playwright/cli@latest

# 驗證，順便讓 agent 看得到指令清單
playwright-cli --help

第一次跑 playwright-cli open 時會自動下載瀏覽器，通常不需要另外裝。完整的安裝流程、skill 安裝、 以及在 Claude Code / Codex 裡的驗證步驟，分別在 第 4 章 到 第 6 章。

ℹ️
本書對應的版本

@playwright/cli 仍在 0.1.x 快速演進中（本書寫作時約 v0.1.19，2026 年 9 月）。指令面在小版本之間持續擴充，書中若某個指令跟你手上的版本對不上，請以 playwright-cli --help 的實際輸出為準。
