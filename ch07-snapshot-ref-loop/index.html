第 7 章 · Part 3：核心操作模型

Snapshot → ref → 操作：核心迴圈

Playwright CLI 的一切都圍著這個三步迴圈轉。

三步迴圈

  1. snapshot——取一份頁面的結構化快照（YAML），裡面每個可互動元素都帶一個 ref，像 e8、e21。
  2. ref——從快照裡挑出你要操作的元素的 ref。
  3. 操作——用 ref 下指令：click e8、fill e8 "..."、check e21。頁面因此改變後，回到第 1 步重新 snapshot。
playwright-cli open https://demo.playwright.dev/todomvc/
playwright-cli snapshot
# 快照存成 YAML，內容像這樣：
#   - textbox "What needs to be done?" [ref=e8]
#   - checkbox "Toggle Todo" [ref=e21]
playwright-cli fill e8 "Write Playwright tests"
playwright-cli press Enter
playwright-cli snapshot        # 頁面變了，重新取
playwright-cli check e21
ℹ️
每個指令後都附一份 snapshot

官方設計：每下一個指令，playwright-cli 都會回一份當前瀏覽器狀態的 snapshot（一行檔案路徑或精簡內容，取決於 outputMode）。你不一定每次都要另外 snapshot，很多時候上一個指令的回傳就夠用。

snapshot 的選項

# 存成固定檔名（當這份快照是工作流成果的一部分時）
playwright-cli snapshot --filename=after-click.yaml

# 只快照某個元素，不是整頁
playwright-cli snapshot "#main"

# 限制深度，省輸出；之後再對某個節點取局部快照
playwright-cli snapshot --depth=4
playwright-cli snapshot e34

# 每個元素附上 bounding box [box=x,y,width,height]
playwright-cli snapshot --boxes

用 find 搜大快照，而不是整份讀

內容豐富的頁面，一份完整 snapshot 可能好幾 KB。find 讓你像 grep -C 一樣搜，只回傳命中的節點加上下各 3 行 context：

playwright-cli find "Add to cart"
playwright-cli find --regex "\$[0-9]+\.[0-9]{2}"
# 正則加旗標時用斜線包起來，例如不分大小寫
playwright-cli find --regex "/sign (in|up)/i"
💡
大頁面別無腦整份 snapshot

先 --depth 拿骨架，或直接 find 你要的字串，再對命中的區域取局部快照。這是把 token 花在刀口上的關鍵習慣。

ref 是短命的

ref 是「從某一次 snapshot 分配出來的」臨時編號，頁面一變動就可能失效。兩個最常見的翻車：

  • 照抄文件裡的 ref。教學寫 check e21，你的頁面那顆 checkbox 可能是 e18。永遠讀你自己那份 snapshot。
  • 操作後沿用舊 ref。導航、送出表單、內容更新之後，先重新 snapshot 再繼續。

需要一個「跨 run 都穩」的定位方式時，改用 role / testId locator，或 generate-locator 把 ref 轉成穩定 locator——這些在 第 9 章 展開。

為什麼這個迴圈省 token

傳統做法是把整份 DOM 或 accessibility tree 塞進模型 context 讓它推理；Playwright CLI 把快照寫成磁碟上的檔案， agent 收到的只是路徑加一句確認，要不要讀、讀多少由 agent 自己決定。它拿到的是 e8 這種精簡引用，直接用，不必處理上萬 token 的樹。 這個帳算下來的差距，見 第 2 章。
