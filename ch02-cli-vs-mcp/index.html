第 2 章 · Part 1：認識 Playwright CLI

Playwright CLI vs Playwright MCP：token 經濟學與選型

同一個團隊、同一顆 Playwright 引擎，兩種餵資料給模型的方式。

Playwright MCP 與 Playwright CLI 都是微軟官方維護的工具，底層跑的是同一顆 Playwright 引擎，做的事情也一樣——開瀏覽器、讀畫面、點按鈕。兩者的差別不在「能不能做」，而在一件很單純的事：AI 讀完一次畫面之後，那份內容放到哪裡去。這個差別聽起來很小，卻直接決定了一段對話能撐幾步、以及一個月的 token 帳單長什麼樣子。

兩種架構：塞進對話 vs 存成檔案

AI 每讀一次頁面，會拿到一份「這一頁有哪些按鈕、輸入框，各自叫什麼名字」的清單——複雜的頁面，這份清單可能長達數千字。兩邊處理這份清單的方式完全相反：

階段Playwright MCPPlaywright CLI
連線／啟動先把全部工具（約 20 幾個）的 JSON schema 送進 context，才能開始對話指令用法寫在一份精簡的 SKILL.md 裡，agent 讀一次就會用
取得畫面內容accessibility tree 整份塞進 tool response，直接進入對話歷史存成 .playwright-cli/*.yml 檔案，對話裡只留一行檔案路徑
截圖圖片 bytes 作為 tool response 回傳，進入 context window存成 PNG 落地磁碟，agent 沒有主動讀取就不會進 context
累積效應每多跑一步，舊的、已經過期的畫面仍留在對話裡每一步都是獨立、帶時間戳的檔案，需要哪一版才開哪一版

CLI 每下一個指令，回應大致是這樣：

playwright-cli goto
$ playwright-cli goto https://example.com

### Page
- Page URL: https://example.com/
- Page Title: Example Domain

### Snapshot
[Snapshot](.playwright-cli/page-2026-02-14T19-22-42-679Z.yml)

注意最後一行——它沒有把整份元素清單倒出來，只給一個檔案路徑。AI 真的要細看時才去開那個檔案；多數時候，它其實只需要上一步 snapshot 給過的 ref（例如 e21），根本不用重新讀。

數字怎麼看：官方 benchmark 約 4 倍差距

Playwright 團隊自己量過同一個任務：走 MCP 大約消耗 114,000 tokens，走 CLI 大約 27,000 tokens，差距約 4 倍。差距的來源正是上一節的兩件事——工具 schema 的一次性開銷，以及 snapshot／截圖是否進入 context。

⚠️
這個數字要當方向看，不要當保證

實際省多少，取決於頁面複雜度、以及 agent 讀了幾次畫面。比省錢更有感的通常是另一件事：對話不會被過期畫面塞滿，agent 能撐更多步而不開始「亂點早就不在畫面上的按鈕」。

可用指令數的落差

因為 CLI 的資料不會塞進 context，官方索性把指令集開得更廣——涵蓋 network mock、tracing、video 錄製、視覺化 dashboard 等 MCP 預設不會開啟的類別。MCP 為了控制 context 大小，預設只啟用一個子集，其餘要額外設定才會出現在工具清單裡。指令數量差距本身就是 CLI 架構帶來的紅利：資料不占 context，自然可以放心多開幾十個指令。

什麼時候用哪一個

三個問題基本上就能決定答案：

問題回答建議
Agent 能不能讀寫檔案、跑 shell 指令？不能（純聊天介面）只能用 MCP
Agent 能不能讀寫檔案、跑 shell 指令？能（Claude Code、Copilot 這類）兩者皆可，看下一題
這趟任務的性質？要邊看邊想、探索沒看過的頁面MCP 比較順——它的即時性有價值
這趟任務的性質？步驟已經清楚，照著做完並留證據CLI 比較划算——尤其超過十幾步之後
💡
務實做法：兩個都用

成熟團隊常見的分工是「MCP 做一次性的理解，CLI 做重複的執行」——面對沒看過的頁面，先用 MCP 探索、讓 agent 邊看邊摸清楚有哪些功能；一旦觀察轉成明確的操作流程，後續的執行、回歸測試、留證，全部交給 CLI。下一章會先釐清一個常見的命名混淆：你在舊教學裡看到的「Playwright CLI」，很可能不是本書講的這個。
