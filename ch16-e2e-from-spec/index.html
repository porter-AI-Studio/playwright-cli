第 16 章 · Part 5：AI Agent 實戰工作流

從測試案例 / charter 到 Playwright 測試檔

先產計畫、標缺口，再落地成重用 Page Object 的測試。

兩階段工作流

  1. 抓步驟 → 產測試計畫。從測試管理系統（或一份 charter / JSON）取得測試案例的詳細步驟， 讓 agent 用 playwright-cli 驅動 live app、把每一步的 YAML snapshot 存到磁碟，產出一份測試計畫文件—— 包含 live DOM 驗證、主要核心工作流、以及被標出來的 gap 與 negative 情境。
  2. 計畫 → Playwright 測試檔。把計畫轉成測試，重用專案裡已經有的 Page Object， 不寫 raw CSS / XPath、不自己新增 Page Object 檔，測試開頭放 // Created By AI 問責標記。

為什麼這樣做又快又省 token

關鍵在第 1 步：agent 驅動 live 應用時，把觀察到的頁面結構存成 YAML 檔，而不是把 raw DOM 貼進對話。 模型看到的是精簡引用和檔案路徑，不是上萬 token 的 DOM——這就是整個流程跑得快、token 帳單低的原因（對照 第 2 章）。

一段可以照著改的 prompt

連到我們的測試管理系統，取得測試案例 290 的詳細步驟。
用 Playwright CLI skill 執行一個兩階段流程：

階段一：驅動 live 應用走一遍，產出測試計畫文件，
        標出主要工作流、live DOM 驗證點、以及缺口與負向情境。
階段二：把測試案例轉成 Playwright 自動化測試。
        重用專案裡既有的 Page Object（login / registration），
        不要自己發明選擇器、不要寫 raw CSS 或 XPath，
        測試第一行加上 // Created By AI。

把 YAML snapshot 留在 test artifacts 目錄當驗證軌跡。

產出物：三份東西

  • 測試計畫——這個案例的名稱、live DOM 驗證、核心工作流步驟，以及 identified gaps and negative scenarios。
  • 測試檔——每個動作與斷言都走既有的 Page Object，沒有 raw selector；agent 沒有新造 Page Object，而是找到你已有的兩個並用它們。
  • paper trail——磁碟上的 YAML snapshot，記錄「驗證了什麼、標記了什麼待查」。
💡
指向 negative validation，不是再產一份 happy path

上一個 station 可能已經用 happy-path 跑過表單，但框架要在入口就守住資料完整性。把這個流程指向「必填欄位驗證」「格式錯誤的 email 被擋下來」這類負向案例，產出的測試對團隊更有價值。

常見踩雷

  • 沒明確要求「重用既有 Page Object」→ agent 自己造一份平行的，之後兩套維護。
  • 沒要求問責標記（// Created By AI）→ 之後分不清哪些測試是 AI 產的。
  • 跳過階段一的計畫與 gap 分析，直接叫它產測試 → 少了「它探索時發現什麼」這個真正的價值。
  • 計畫階段目標頁進不去（要登入、要資料）→ 先處理 storage state（第 10 章）。
